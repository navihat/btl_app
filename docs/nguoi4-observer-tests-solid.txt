1. Ý TƯỞNG VÀ LÝ DO LỰA CHỌN
--------------------------------------------------------------

Người 4 chịu 3 nhiệm vụ chính:
  (A) Observer Pattern: lắng nghe sự kiện tạo/xóa đề thi
  (B) Toàn bộ 32 unit tests với mock repositories
  (C) Rà soát SOLID, ghi chú vị trí áp dụng cho báo cáo

Tại sao chọn Observer cho quản lý đề thi?
  Khi ExamService tạo hoặc xóa đề thi, có thể có nhiều
  "bên quan tâm" cần được thông báo:
    - UI component muốn cập nhật số lượng hiển thị
    - Logger muốn ghi lại lịch sử thay đổi
    - Cache muốn invalidate

  Nếu hard-code vào ExamService:
    async createExam(dto) {
      ...
      await logger.log(exam)         ← ExamService biết về Logger?
      await cache.invalidate()       ← vi phạm SRP, OCP
      ui.refresh()
    }
  → ExamService phải import và biết về mọi "bên quan tâm".
  → Thêm một subscriber mới phải sửa ExamService.

  Observer Pattern giải quyết:
    ExamService chỉ gọi examSubject.notify('created', exam)
    → ExamSubject tự phân phối đến tất cả subscriber đã đăng ký
    → Thêm subscriber mới: subject.subscribe(new MyObserver())
    → Không sửa ExamService

Tại sao viết unit test với mock repository?
  - Unit test phải nhanh và cô lập: không đọc/ghi file thật.
  - InMemoryRepository lưu data trong mảng RAM → tốc độ nanosecond.
  - Có thể kiểm tra nội bộ (repo.getAll()) mà JsonRepository
    không cần cung cấp method đó.
  - Khi test thất bại, chắc chắn là do logic sai, không phải
    do file I/O hay path sai.

Chiến lược kiểm tra:
  - Test happy path: kết quả đúng khi input hợp lệ
  - Test error path: throw đúng message khi input sai
  - Test side effect: repo thực sự được gọi với đúng data
  - Test observer: spy function được gọi đúng số lần

4. CHI TIẾT OBSERVER PATTERN
--------------------------------------------------------------

---- src/patterns/observer/IExamObserver.ts ----

  interface IExamObserver {
    update(event: 'created' | 'deleted', exam: Exam): void
  }

Bất kỳ class nào muốn "nghe" sự kiện đề thi đều phải
implements interface này. Đây là contract duy nhất giữa
Subject và Observer.


---- src/patterns/observer/ExamSubject.ts ----

Subject (Publisher) quản lý danh sách observer.

  private observers: IExamObserver[] = []

  subscribe(observer):
    Kiểm tra !includes trước khi push → tránh đăng ký trùng

  unsubscribe(observer):
    filter() loại bỏ observer khỏi mảng

  notify(event, exam):
    Duyệt tất cả observers, gọi observer.update(event, exam)
    → Theo thứ tự đăng ký

  getObserverCount():
    Trả về số lượng observer đang đăng ký (dùng trong test)

ExamService giữ một instance của ExamSubject:
  Sau createExam(): examSubject.notify('created', exam)
  Sau deleteExam(): examSubject.notify('deleted', exam)


---- src/patterns/observer/ExamListObserver.ts ----

Concrete Observer lưu snapshot danh sách đề thi.

  private exams: Exam[] = []
  private lastEvent: {type, exam} | null = null

  update(event, exam):
    Lưu lastEvent (để debug / test)
    if 'created': push exam vào exams
    if 'deleted': filter() loại bỏ exam khỏi exams

  getExams(): Exam[]
    Trả về copy của danh sách (spread để tránh mutation ngoài)

  getLastEvent()
    Trả về event cuối cùng nhận được

Ứng dụng thực tế:
  → Có thể dùng để sync UI mà không cần gọi lại IPC
  → Có thể làm ActivityLogger ghi lịch sử thao tác
  → Mở rộng: EmailNotificationObserver gửi mail khi tạo đề

5. CHI TIẾT MOCK REPOSITORIES
--------------------------------------------------------------

---- src/tests/mocks/InMemoryQuestionRepository.ts ----

Implements IQuestionRepository với mảng RAM.

  private store: Question[] = []

  constructor(initial: Question[] = [])
    → Khởi tạo với dữ liệu mẫu cho test

  findAll(filter?): async
    Lọc giống JsonQuestionRepository nhưng không đọc file

  findById(id): async
    Array.find() → null nếu không có

  save(question): async
    store.push(question)

  update(question): async
    findIndex → store[idx] = question

  delete(id): async
    store = store.filter(q => q.id !== id)

  getAll(): Question[]   ← THÊM method này để test kiểm tra state
    return [...store]


---- src/tests/mocks/InMemoryExamRepository.ts ----

Tương tự cho Exam.

  getAll(): Exam[]   ← dùng để assert số lượng sau create/delete


---- src/tests/mocks/fixtures.ts ----

Hàm tạo test data để tái sử dụng.

  makeQuestion(overrides?):
    Trả về Question hợp lệ với giá trị mặc định.
    overrides: ghi đè bất kỳ field nào.

    Ví dụ:
      makeQuestion()
      → { id: 'q-1', content: 'Câu hỏi mẫu?', ... }

      makeQuestion({ id: 'q-custom', difficulty: Difficulty.Hard })
      → { id: 'q-custom', difficulty: 'hard', ... }

  makeExam(overrides?):
    Tương tự cho Exam.
    questionIds: []  ← mặc định rỗng

7. SOLID REVIEW – VỊ TRÍ ÁP DỤNG CHO BÁO CÁO
--------------------------------------------------------------

S – Single Responsibility Principle (SRP)
  ─────────────────────────────────────────
  File: QuestionService.ts
  Lý do: Chỉ điều phối nghiệp vụ câu hỏi (create, update, delete,
  list). Không xử lý file I/O, không tạo UUID, không validate
  format. Khi quy tắc nghiệp vụ thay đổi → sửa file này.

  File: JsonQuestionRepository.ts
  Lý do: Chỉ đọc/ghi questions.json. Không có logic nghiệp vụ,
  không biết validation, không biết UUID. Khi cách lưu trữ thay
  đổi (sang SQLite) → tạo class mới, không sửa service.

  File: QuestionFactory.ts
  Lý do: Chỉ tạo object Question hợp lệ. Không lưu trữ, không
  điều phối workflow.

  File: ExamBuilder.ts
  Lý do: Chỉ xây dựng và validate cấu trúc Exam. Không lưu trữ.

O – Open/Closed Principle (OCP)
  ─────────────────────────────────────────
  File: IQuestionSelectionStrategy.ts
  Lý do: ExamService.addQuestions() gọi strategy.select() mà
  không biết implementation cụ thể. Thêm cách chọn câu mới:
    - ManualSelectionStrategy ✓ (hiện tại)
    - RandomSelectionStrategy (tương lai)
    - ByTopicSelectionStrategy (tương lai)
  → Chỉ tạo class mới, ExamService.ts KHÔNG thay đổi dòng nào.

  File: IQuestionFactory.ts
  Lý do: Có thể tạo MultipleChoiceQuestionFactory,
  TrueFalseQuestionFactory mà không sửa QuestionService.

D – Dependency Inversion Principle (DIP)
  ─────────────────────────────────────────
  File: QuestionService.ts
  Lý do: Constructor nhận IQuestionRepository (không phải
  JsonQuestionRepository) và IQuestionFactory (không phải
  QuestionFactory). High-level module (service) phụ thuộc vào
  abstraction, không phụ thuộc vào detail (JSON file).

  File: ExamService.ts
  Lý do: Nhận IExamRepository, IQuestionRepository, IExamBuilder,
  IQuestionSelectionStrategy — toàn bộ là interface.
  → Khi test: inject InMemory* (nhanh)
  → Khi chạy thật: inject Json* (có file)
  → ExamService không cần thay đổi gì.

  Minh họa DIP bằng code:
    // HIGH-LEVEL (service) phụ thuộc abstraction
    class QuestionService {
      constructor(
        private repo: IQuestionRepository,   ← abstraction
        private factory: IQuestionFactory     ← abstraction
      ) {}
    }

    // LOW-LEVEL (detail) implements abstraction
    class JsonQuestionRepository implements IQuestionRepository { ... }
    class InMemoryQuestionRepository implements IQuestionRepository { ... }

    // WIRING (serviceFactory) kết nối high với low
    new QuestionService(
      new JsonQuestionRepository(...),  ← detail
      new QuestionFactory()             ← detail
    )

8. CÁC LỖI THƯỜNG GẶP KHI VIẾT TEST
--------------------------------------------------------------

Lỗi 1: Quên await trong test async
  SAI:  const q = service.createQuestion(dto)  ← Promise, không phải Question
  ĐÚNG: const q = await service.createQuestion(dto)

Lỗi 2: Dùng expect(fn).toThrow() cho async function
  SAI:  expect(service.createQuestion({...})).toThrow(...)
  ĐÚNG: await expect(service.createQuestion({...})).rejects.toThrow(...)

Lỗi 3: Không reset state giữa các test
  ĐÚNG: Dùng beforeEach để tạo repository mới mỗi test:
    let service: QuestionService
    beforeEach(() => {
      service = makeService([])
    })
  Hoặc dùng function makeService() trong từng it() block.

Lỗi 4: vi.fn() không reset giữa test
  ĐÚNG: Khai báo mock mới trong mỗi test, hoặc vi.clearAllMocks()
    trong beforeEach.

Lỗi 5: toThrow() match partial string
  expect(...).toThrow('q-999')
  → Vitest kiểm tra message.includes('q-999')
  → Không cần match toàn bộ message.
